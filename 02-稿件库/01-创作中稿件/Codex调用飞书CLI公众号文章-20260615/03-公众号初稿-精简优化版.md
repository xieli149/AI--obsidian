# AI 不只会写代码：接上飞书 CLI 后，Codex 才真的像工作助手

![Codex 调用飞书 CLI 的工作流封面](assets/01-cover-codex-lark-cli.png)

很多人现在用 AI 写东西，最麻烦的地方其实不是 AI 不会写。

而是资料太分散。

会议纪要在飞书，选题表在飞书，项目资料也在飞书。等你真要让 AI 帮你整理时，又开始手动复制、粘贴、再复制、再粘贴。

这一来一回，AI 没省多少时间，人先累了。

所以我最近觉得，Codex 接上飞书 CLI 这件事，对运营人和内容人挺有用。

先说清楚，不是让你去背命令。

命令应该由 Codex 自己调用。

你真正需要理解的是：**飞书 CLI 给了 Codex 一条“进入飞书资料”的路。**

## 这件事到底是什么？

![Codex 调用 lark-cli 的执行链路](assets/02-workflow.png)

可以把它拆成三层来看。

| 工具 | 它负责什么 | 你可以怎么理解 |
| --- | --- | --- |
| 飞书 | 存文档、表格、会议纪要、素材 | 你的工作资料库 |
| `lark-cli` | 把飞书能力变成电脑能执行的命令 | 一条通向飞书的通道 |
| Codex | 判断任务、调用命令、整理结果 | 真正替你干活的人 |

以前你让 AI 看飞书资料，往往要先把内容复制出来。

现在可以变成你直接说：

```text
读取这篇飞书文档，帮我整理成公众号文章大纲。
```

Codex 会自己判断：这是文档读取任务，要通过飞书 CLI 去拿内容。拿到以后，再按你的要求整理。

所以重点不是“我会不会命令行”。

重点是：**你的飞书资料终于可以被 AI 调用了。**

## 那 CLI 命令还有必要懂吗？

有必要。

但不是为了让你手敲。

而是为了你知道 Codex 背后在做什么，不至于它一动飞书，你完全不知道它在动哪里。

![lark-cli 高频命令卡片](assets/03-command-cards.png)

举几个最常见的：

| Codex 想做的事 | 背后常用的命令 | 你要理解的意思 |
| --- | --- | --- |
| 检查飞书 CLI 能不能用 | `lark-cli doctor` | 先看工具本身是否正常 |
| 看当前有没有登录 | `lark-cli auth status` | 确认 Codex 有没有权限访问飞书 |
| 读取一篇飞书文档 | `docs +fetch` | 把文档内容取出来给 AI 分析 |
| 搜索飞书里的资料 | `drive +search` | 按关键词找历史文档和素材 |
| 判断一个飞书链接是什么 | `drive +inspect` | 先看它是文档、表格、Wiki 还是文件 |
| 写回飞书文档 | `docs +update` | 把整理好的内容追加或更新回文档 |

你不用背这些命令。

但你最好知道它们大概分成三类：

**检查环境、读取资料、写回资料。**

这三个动作的风险不一样。

检查环境几乎没风险。

读取资料风险也比较低。

写回资料就要谨慎，因为它真的会改你的飞书内容。

这也是为什么我更建议新手先从“读取”和“搜索”开始，不要一上来就让 AI 覆盖文档。

## Codex 真正帮你省的是这部分时间

![运营人适合落地的 3 个场景](assets/04-use-cases.png)

对运营人来说，最适合先跑的不是复杂自动化，而是这些很具体的小任务。

比如你开完会，飞书里有一篇会议纪要。以前你要复制出来，再让 AI 总结。现在你可以直接让 Codex 读取文档，提炼出适合公众号的选题、标题和核心观点。

再比如你做内容复盘，想找之前提过的“AI 工作流”“语音输入”“选题池”。你不用自己翻一堆飞书文档，可以让 Codex 通过 `drive +search` 先搜，再帮你筛出有用的资料。

还有一种很实用：你在 Obsidian 写稿，本地有 Markdown、图片、发布包；飞书适合归档和协作。后面就可以让 Codex 把本地资料同步或整理到飞书里。

这些事情单独看都不难。

但很碎。

而碎活，正适合交给 Codex。

你负责判断“我要什么结果”。

Codex 负责找资料、跑命令、整理成可用内容。

## 使用时记住一个原则

![Codex 调用飞书 CLI 前的安全检查清单](assets/05-safety-checklist.png)

让 Codex 调飞书 CLI，不代表什么都可以放心交出去。

我会把任务分成两种：

一种是只读任务，比如读取文档、搜索资料、查看链接类型。这类适合大胆用。

另一种是写入任务，比如更新文档、同步文件夹、删除文件、改权限。这类要慢一点。

如果 Codex 准备写入飞书，我建议先看 4 个问题：

1. 它要动的是哪篇文档？
2. 它是追加、覆盖，还是删除？
3. 有没有备份，能不能先 `dry-run`？
4. 改错以后能不能恢复？

这不是把 AI 想得很危险。

而是把边界说清楚。

边界越清楚，AI 越好用。

## 新手可以直接这样对 Codex 说

你不用自己写命令，可以把目标说完整一点：

```text
我想让你通过 lark-cli 读取飞书资料。

请先检查 lark-cli 是否可用，再读取匹配的飞书 skill。
这次只做读取和整理，不要写回、覆盖或删除任何飞书内容。

目标：
读取这篇飞书文档，整理成公众号文章大纲。

文档链接：
<粘贴飞书文档链接>
```

这段话的重点是让 Codex 明白三件事：

先检查环境。

先读规则。

这次只读，不写回。

你不用懂每个参数，但你要知道自己把什么权限交给了 AI。

## 最后说一句

Codex 接上飞书 CLI 以后，最大的变化不是“多了一个工具”。

而是你的工作资料不再只是躺在飞书里。

它可以被读取、被搜索、被整理，也可以在你确认后写回。

这对内容人很重要。

因为我们的很多工作，本质上不是从零创作，而是把散落的资料重新组织成一篇文章、一张表、一个选题池。

以前你在飞书、AI 对话框、Obsidian 之间来回搬运。

现在可以试着让 Codex 接手中间那段碎活。

先不用做复杂自动化。

就从一个最简单的任务开始：

**读取一篇飞书文档，整理成一份公众号大纲。**

这一步跑通以后，你会明显感觉到：AI 不只是会写几段话，它开始能进入你的真实工作流了。
